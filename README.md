# ПОС — Преподавательская Оценка Студентов

Консольное приложение на C# (.NET 10) для учёта преподавательской оценки студентов: студенты, рубрикатор критериев, выставление и исправление оценок, расчёт итога по весам и выгрузка итогов в CSV. Домен построен по DDD, архитектура — Ports and Adapters, паттерны GoF — по одному из каждой группы

## Логика решений

### Структура проекта

```
src/Pos.ConsoleApp/       меню, ввод-вывод, демо-сценарий, настройка DI-контейнера
src/Pos.Core/
  Domain/                 ядро (сущности, value objects, инварианты, фабрика, domain service, порты репозиториев)
  Application/            сценарии и порт экспорта
  Infrastructure/         адаптеры (репозитории в памяти, CSV-экспорт)
tests/Pos.Tests/          юнит-тесты инвариантов, domain service, фасада и DI
```

Консоль вынесена в отдельный проект (`Pos.Core` ничего не знает о вводе и выводе, поэтому его можно проверять тестами)

### Карта DDD

`Student` (студент)
`Criterion` (критерий)
`Rubric` (рубрикатор)
`Evaluation` (оценка)
`Score` (балл)
 итог — результат `TotalScoreService`

| Понятие | Тип | Почему так |
|---|---|---|
| `Student` | Entity | у студента есть идентичность (два студента с одинаковым именем — разные люди) |
| `Criterion` | Entity (внутри агрегата `Rubric`) | критерий можно переименовать, он останется тем же критерием, создаётся только рубрикатором (`internal` конструктор — снаружи `Pos.Core` не вызвать) |
| `Rubric` | Aggregate root | набор критериев курса, охраняет уникальность названий (пока курс один — рубрикатор один) |
| `Evaluation` | Entity | студенту по критерию поставили балл (идентичность — пара (студент, критерий), поэтому отдельного id нет), создаётся только через `EvaluationFactory` (`internal` конструктор) |
| `Score` | Value Object | балл без идентичности: `new Score(7) == new Score(7)` (не может быть отрицательным) |
| `StudentId`, `CriterionId` | Value Object | типизированные идентификаторы — компилятор не даст перепутать id студента с id критерия |

**Entity vs Value Object на примере** 
`Student` — Entity: если двух студентов зовут одинаково, это всё равно два разных студента, их различает `StudentId`

 `Score` — Value Object: балл 7 у одного студента и балл 7 у другого студента неразличимы, важно только значение
 
  Поэтому `Score` — `readonly record struct` с равенством по значению, а `Student` — класс с `Id`

**Инварианты:**

| Правило | Где охраняется |
|---|---|
| балл не отрицательный | конструктор `Score` |
| балл не выходит за максимум критерия | `EvaluationFactory.Create` |
| оценка только по критерию из рубрикатора | `EvaluationFactory.Create` через `Rubric.Get` |
| названия критериев не повторяются (максимум и вес положительные) | `Rubric.AddCriterion`, конструктор `Criterion` |
| итог согласован с текущими оценками и рубрикатором | `TotalScoreService.Calculate` считает итог заново по оценкам студента и проверяет, что все они — по критериям рубрикатора |

Итог не хранится как отдельная цифра — он всегда вычисляется из оценок и рубрикатора

**Repository (порты)** — `IStudentRepository`, `IRubricRepository`, `IEvaluationRepository` в `Domain/Repositories.cs` (домен знает только интерфейсы, а реализации — в `Infrastructure/InMemoryRepositories.cs`)

**Domain Service** — `TotalScoreService`: правило расчёта итога не принадлежит ни студенту, ни оценке, ни критерию, оно про их совместную работу. Итог считается по 10-балльной шкале: доля от максимума по каждому критерию, умноженная на вес, делённая на сумму весов. Веса относительные: `0.5/0.3/0.2` и `50/30/20` дают один результат

### Архитектура: Ports and Adapters

```
      Pos.ConsoleApp (адаптер UI + корень сборки в Program.cs)
            │
      Application: GradingFacade, StudentTotal, порт IResultsExporter
            │
      Domain: Student, Criterion, Rubric, Evaluation, Score,
              EvaluationFactory, TotalScoreService + ITotalStrategy,
              порты IStudentRepository / IRubricRepository / IEvaluationRepository
            │  реализует порты
      Infrastructure: InMemory*Repository, CsvResultsExporter
```

Все стрелки направлены внутрь, к домену:
- `Domain` не использует ничего из `Application` и `Infrastructure` — ни одного `using Pos.Core.Application` / `Pos.Core.Infrastructure` в этой папке нет (про файлы, консоль и CSV домен не знает)
- `Application` использует только `Domain`
- `Infrastructure` использует `Domain` и `Application` только ради портов, которые реализует
- `Pos.ConsoleApp` видит всё, потому что это корень сборки: в `Program.cs` порты связываются с адаптерами

Что это даёт - CSV-экспорт можно заменить на JSON, а хранение в памяти — на файл, поменяв одну строку в `Program.cs`, домен и тесты не заметят (в тестах порт экспорта подменяется фейком `FakeResultsExporter`)

### Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `Domain/EvaluationFactory.cs` | единственная точка создания оценки: проверяет, что критерий есть в рубрикаторе и балл в диапазоне `[0, MaxScore]`. Конструктор `Evaluation` — `internal`, поэтому снаружи `Pos.Core` (из консоли, тестов) обойти фабрику и создать 12 из 10 нельзя |
| Структурный | **Facade** | `Application/GradingFacade.cs` | консоль вызывает `facade.Grade(...)`, `facade.GetTotals()` и не знает про репозитории, фабрику и domain service. Без фасада каждая ветка меню сама собирала бы объекты, и логика сценариев размазалась бы по UI. Фасад — единственная точка входа для любого UI, не только консоли |
| Поведенческий | **Strategy** | `Domain/TotalStrategies.cs` | правило итога сменяемое: `WeightedTotalStrategy` (неоценённый критерий = 0, для конца курса) и `GradedOnlyTotalStrategy` (нормировка только по оценённым, для середины курса). `TotalScoreService` не меняется при добавлении нового правила — выбор делается в `Program.cs` |

Паттернов ровно три — по одному на группу. Builder для рубрикатора не нужен: критерии добавляются по одному через меню, и валидность каждого проверяется сразу в `Rubric.AddCriterion`. Decorator для округления не нужен: округление — вопрос вывода, оно делается форматированием в консоли и CSV, а не в домене

### Исправление и отмена оценки

`Evaluation` неизменяемая. Исправить оценку = выставить новую по тому же критерию: фасад удаляет прежнюю и сохраняет новую. Так у пары студент–критерий всегда не больше одной оценки, и исправленная оценка проходит те же проверки фабрики, что и первая. Отменить — `CancelEvaluation(студент, критерий)` удаляет оценку из репозитория

### DI-контейнер

Зависимости настраиваются в `Program.cs` через `Microsoft.Extensions.DependencyInjection`. Классы не создают зависимости сами, а получают их через конструктор: `GradingFacade` получает три репозитория, `EvaluationFactory`, `TotalScoreService` и `IResultsExporter`; `TotalScoreService` получает `ITotalStrategy`. Всё зарегистрировано как `Singleton`, чтобы фасад и демо-сценарий работали с одними и теми же хранилищами

### Тесты

| Файл | Что проверяет |
|---|---|
| `ScoreTests` | отрицательный балл невозможен, равенство по значению |
| `RubricTests` | дубликаты названий (с учётом регистра и пробелов), неположительные максимум и вес, поиск по id |
| `EvaluationFactoryTests` | балл 0, 5, 10 из 10 проходит (11, 12, 100, −1 и критерий из чужого рубрикатора — нет) |
| `TotalScoreServiceTests` | взвешенный итог `8.2` для оценок 8/10, 5/5, 6/10 с весами 0.5/0.3/0.2, неоценённый критерий как 0, `GradedOnlyTotalStrategy` даёт 8.0 вместо 4.0, а оценка по критерию не из рубрикатора — ошибка |
| `GradingFacadeTests` | повторная оценка заменяет прежнюю, неверный балл не трогает существующую, отмена, итоги по всем студентам, экспорт через порт |
| `DependencyInjectionTests` | контейнер собирает фасад с общими репозиториями (подмена стратегии в контейнере меняет итог) |

## Запуск

```
dotnet build                                  # собрать проект
dotnet run --project src/Pos.ConsoleApp       # запустить приложение
dotnet test                                   # запустить тесты
```

После запуска появляется меню:

| Пункт | Выполняет |
|---|---|
| 1 | добавить студента |
| 2 | добавить критерий в рубрикатор (название, максимальный балл, вес) |
| 3 | показать студентов и рубрикатор |
| 4 | выставить оценку (повторная оценка по тому же критерию исправляет прежнюю) |
| 5 | показать оценки студента и его итог |
| 6 | отменить оценку |
| 7 | итоги по всем студентам |
| 8 | экспорт итогов в CSV (студент;итог) |
| 9 | демо: сквозной сценарий |
| 0 | выход |

**Демо-сценарий (пункт 9)** на пустых данных заводит трёх студентов и три критерия, выставляет оценки, исправляет одну, пробует нарушить правила (12 из 10, отрицательный балл, критерий не из рубрикатора — все попытки отклоняются), печатает итоги и сохраняет `demo-results.csv`

Если ввести что-то неправильное (буквы вместо числа, пустую строку), программа просит ввести значение заново. Балл при выставлении оценки нарочно не ограничивается на уровне ввода — чтобы было видно, как инвариант срабатывает в домене
